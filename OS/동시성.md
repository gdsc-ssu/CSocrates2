> **동시성은 "상황", 동기화는 그 상황의 안전 문제를 푸는 "일", 뮤텍스·세마포어는 그 일을 해내는 "도구", 교착 상태는 도구를 잘못 써서 생기는 "부작용".** 그리고 오늘날 서버는 이 OS 도구함을 "서버 한 대로 수만 연결"이라는 극한에 적용한 엔지니어링이다.

## 1. OS 동시성이란

### 1.1 왜 필요한가

- **CPU는 미친 듯이 빠르고, 그 외 모든 것(디스크·네트워크·사용자 입력)은 느리다.** CPU가 1초에 수십억 번 연산하는 동안 네트워크 응답 한 번은 수 ms~수백 ms.
- 작업을 하나씩 순서대로만 처리하면, 느린 걸 기다리는 동안 CPU가 논다 → 비싼 자원 낭비.
- **동시성 = "한 작업이 느린 걸 기다리는 동안 다른 작업을 시켜 CPU를 놀리지 말자".** 나머지는 전부 "이걸 어떻게 잘하느냐"의 디테일.

### 1.2 실행 단위

- **프로세스**: 독립된 메모리 공간. 서로 침범 못 해 안전하지만, 통신은 IPC 필요, 생성 비용 큼.
- **스레드**: 한 프로세스 안에서 메모리(코드·데이터·힙)를 **공유**하는 더 가벼운 단위. 통신은 공짜지만, 바로 그 "같이 본다"가 모든 동기화 문제의 씨앗.
- **핵심:** OS 스레드는 **커널이 관리하는 자원**이다. 하나당 보통 **1~8MB 스택** + 스케줄러 관리 대상 하나. → "스레드는 공짜가 아니다"가 뒤에서 **C10K 문제**로 폭발한다.

### 1.3 스케줄러와 컨텍스트 스위칭

- 스레드는 여러 개, 코어는 한정 → **스케줄러**가 짧은 시간(타임 슬라이스)씩 번갈아 실행. 너무 빨라 사람 눈엔 "동시"로 보임.
- **컨텍스트 스위칭은 비싸다:** A→B 전환 시 레지스터·스택 상태 저장/복원 + 커널 모드 전환 + **CPU 캐시가 식음**. 수만 개가 마구 전환되면 "일"보다 "전환"에 시간을 더 쓴다.
- **블로킹되면 스케줄러가 그 스레드를 재운다:** CPU에서 빼두고 다른 스레드를 올림. 대기가 끝나면 깨워서 실행 큐에 넣음. → 이 **"멈췄다 깨우기"** 를 기억하라. 나중에 **async/await가 유저공간에서 똑같은 일을 흉내** 낸다.

### 1.4 블로킹 I/O

- 평범한 `read(socket)`은 데이터가 올 때까지 **그 스레드를 멈춘다(블로킹)**. 그동안 스레드는 일 못 하면서 메모리·스케줄러 슬롯만 차지.
- 작업이 몇 개면 OK → 전통적 서버는 **연결 하나당 스레드 하나(thread-per-connection)**. 가장 직관적인 답.
- 이 직관이 **어디서 무너지는가**가 백엔드 동시성의 출발점(→ 3장).

### 1.5 동시성이 낳는 문제

1. **효율 문제** — 여러 작업을 어떻게 잘 굴릴까: 스레드·스케줄러·블로킹/논블로킹 I/O. (동기화와 무관, → 3장)
2. **안전 문제** — 공유 자원을 어떻게 안전하게 나눠 쓸까: **이것이 곧 동기화** (→ 2장)

## 2. 동기화

### 2.1 왜 필요한가: 경쟁 상태(Race Condition)

- `count++` 한 줄도 기계 수준에선 **읽기 → +1 → 쓰기** 3단계.
- 스레드 A가 읽은 직후 쓰기 전에 B가 끼어들어 같은 값을 읽으면 → 둘 다 같은 값에 +1 → **두 번 증가가 한 번으로 사라짐**.
- 실행 순서에 따라 결과가 달라지는 이 버그가 **경쟁 상태**.

### 2.2 임계 구역(Critical Section)

공유 자원에 접근하는 코드 영역. 올바른 보호는 세 조건을 만족해야 함:

1. **상호 배제(Mutual Exclusion)** : 한 번에 한 스레드만 진입
2. **진행(Progress)** : 아무도 없으면 들어가려는 스레드 중 하나는 들어가야 함
3. **한정 대기(Bounded Waiting)** : 무한정 기다리지 않게 보장

> 여기까지가 교과서의 "무엇". 아래 2.3~2.5는 그 "어떻게"를 바닥(하드웨어·메모리)까지 내려가 본다. "락을 쓴다"가 실제로 무슨 일인지 알아야 도구를 제대로 다룰 수 있다.

### 2.3 상호 배제 한계

**순진한 해법은 전부 깨진다.** "내 차례 변수 하나 두면 되지 않나?" 싶지만, 두 스레드가 그 변수를 **읽고-쓰는 사이에** 서로 끼어들어 둘 다 임계구역에 들어간다. 단일 플래그·교대 turn 변수 같은 시도는 상호 배제·진행·한정 대기 중 하나를 반드시 위반한다.

**Peterson 알고리즘** — 두 스레드에 한해, 공유 변수만으로 세 조건을 모두 만족하는 고전 해법:

```
flag[i] = true;                 // 나 들어가고 싶다
turn = j;                       // 근데 양보는 너 먼저
while (flag[j] && turn == j) ;  // 상대도 원하고 지금 상대 차례면 대기
   // --- 임계 구역 ---
flag[i] = false;
```

아이디어는 **"나 원한다(flag)"와 "양보한다(turn)"를 결합**해 데드락·기아를 막는 것. 시험 단골 증명 대상이다.

**그런데 현대 CPU에서 그냥은 안 돈다.** Peterson 증명은 "메모리 연산이 코드 순서대로, 즉시 모두에게 보인다(순차 일관성)"를 가정한다. 실제 CPU·컴파일러는 성능을 위해 **연산을 재배치**한다. `flag[i]=true`와 `turn=j`의 순서가 다른 코어 시점에서 뒤바뀌어 보이면 상호 배제가 깨진다. → 소프트웨어-온리 상호 배제는 **메모리 배리어 없이는 불안정**하다. 그래서 하드웨어 지원(2.4)과 메모리 모델(2.5)이 필요하다. 교과서가 Peterson 다음에 곧장 하드웨어 원자 명령으로 넘어가는 이유다.

### 2.4 하드웨어 원자성

락·세마포어·모니터는 전부 CPU의 원자 명령 위에 지어진다.

**세 가지 원자 명령**

- **Test-and-Set (TAS)**: 값을 1로 세팅하면서 **이전 값을 반환**. "잠그고, 원래 잠겨 있었는지 알려줘"를 한 번에.
- **Compare-and-Swap (CAS)**: `CAS(addr, expected, new)` — 값이 `expected`면 `new`로 바꾸고 성공 반환. **lock-free의 심장.**
- **Fetch-and-Add (FAA)**: 원자적으로 더하고 이전 값 반환. 카운터·티켓 락에 씀.

원자적인 이유는 실행 순간 CPU가 캐시 라인/버스를 독점(cache line lock)하기 때문.

**TAS로 스핀락 짓기 - 그리고 왜 느린가**

```
lock:   while (TestAndSet(&l) == 1) ;   // 잠겨 있으면 계속 시도
unlock: l = 0;
```

TAS는 매번 **쓰기**라, 여러 코어가 스핀하면 캐시 라인 소유권이 코어 사이를 계속 튕겨다닌다(cache line bouncing) → 버스 마비. 개선책이 **TTAS(Test-and-Test-and-Set)**:

```
while (l == 1 || TestAndSet(&l) == 1) ; // 먼저 '읽기'로 눈치보다, free일 때만 TAS
```

스핀 대부분을 **로컬 캐시 읽기**로 처리해 버스 트래픽을 줄인다. "스핀락도 순진하게 짜면 느리다"가 실전 감각.

**티켓 락 - 공정성 추가.** 순수 스핀락은 운 나쁜 스레드가 영영 못 잡는(기아) 문제가 있다. FAA로 번호표를 뽑고 순서대로:

```
my = FetchAndAdd(&next, 1);   // 번호표
while (now_serving != my) ;   // 내 번호 될 때까지
   // 임계 구역
now_serving++;                // 다음 사람
```

은행 번호표 그대로, **FIFO 공정성** 확보.

**진짜 뮤텍스 = 스핀 + 재우기(futex).** 스핀은 짧게 잡을 때만 유리(계속 CPU 태움). 길게 기다릴 거면 재워야 한다. 그래서 실제 뮤텍스는 하이브리드다.

- **경합 없음(fast path)**: 유저공간에서 **CAS 한 번**으로 잠금 끝, 커널 안 감. → uncontended 락이 "거의 공짜"인 이유.
- **경합 있음(slow path)**: 리눅스 **futex**로 커널에 "나 재워줘"(`futex_wait`), unlock 시 `futex_wake`로 깨움.

→ "락은 느리다"는 미신의 정확한 반박: 느린 건 락이 아니라 **경합**이다. 최적화는 락을 없애는 게 아니라 **락 잡는 구간을 짧게·잘게** 쪼개 경합을 줄이는 것.

### 2.5 메모리 모델 

락이 "안전하다"는 말에는 사실 **세 가지 다른 보장**이 섞여 있다. 이걸 분리하는 게 심화의 핵심.

- **원자성(Atomicity)**: `count++`가 중간에 안 쪼개진다.
- **가시성(Visibility)**: 한 코어가 쓴 값을 다른 코어가 본다.
- **순서(Ordering)**: 코드에 적은 순서대로 메모리 연산이 보인다.

**재배치는 정상이다.** 컴파일러·CPU는 성능을 위해 메모리 연산 순서를 바꾼다. 대표적으로 **스토어 버퍼**: 쓰기를 버퍼에 넣고 CPU는 다음 명령으로 진행 → 다른 코어엔 그 쓰기가 늦게 보인다.

**순차 일관성(SC)이라는 이상, 그리고 현실.** SC는 모든 코어가 "하나의 전역 순서"로 메모리 연산을 보는 세계 — 우리가 코드 짤 때 _가정하는_ 것. 현실은 x86조차 TSO(store→load 재배치 허용), ARM·POWER는 더 약하다(weak ordering). 고전 반례(store buffering):

```
초기 x = y = 0
코어1: x = 1;  r1 = y;
코어2: y = 1;  r2 = x;
```

SC라면 `r1==0 && r2==0`은 불가능(둘 중 하나는 상대 쓰기를 봐야 함). **그러나 실제 x86에서 이 결과가 나온다** — 각자의 쓰기가 스토어 버퍼에 갇혀 서로 못 본 채 옛 값을 읽어서. 2.3에서 Peterson이 깨지는 게 정확히 이 현상이다.

**메모리 배리어 / acquire-release.** 재배치를 막는 울타리가 배리어(fence)다. 실전 두 개념:

- **acquire(획득)**: 이 연산 _뒤_의 접근이 _앞_으로 못 넘어옴 → **락 획득**에 씀.
- **release(해제)**: 이 연산 _앞_의 접근이 _뒤_로 못 넘어감 → **락 해제**에 씀.

락을 acquire로 잠그고 release로 풀면, 임계구역 안의 쓰기들이 "잠금~해제" 사이에 갇히고, 다음에 그 락을 acquire한 스레드가 그 쓰기들을 **반드시 본다**. 이 성립이 **happens-before**다. → 뮤텍스만 쓰면 가시성·순서까지 공짜로 챙겨지는 이유. 라이브러리가 배리어를 심어둔 것.

**언어별 메모리 모델**

- **Java(JMM)**: `volatile` 쓰기=release, 읽기=acquire. 모니터 unlock→lock, `Thread.start`/`join`이 happens-before를 만든다. "`volatile`은 원자성이 아니라 가시성·순서 보장"이 핵심 오해 포인트.
- **C++**: `std::memory_order_{relaxed, acquire, release, acq_rel, seq_cst}`. 기본 seq_cst(가장 강·비쌈), 성능 필요 시 relaxed로 내림.
- **Go**: `sync/atomic` + 채널·뮤텍스가 happens-before를 정의. "메모리를 공유하지 말고 통신하라"의 형식적 근거.

**요약:** 원자성 ≠ 가시성 ≠ 순서. 락은 셋 다 준다. 직접 만든 플래그는 배리어 없이는 원자성만 있고 나머지가 깨진다.

### 2.6 동기화 도구

> **동기화**는 "교통정리를 한다"는 목적이고, 아래 도구들은 그걸 해내는 연장이다. 이제 각 도구를 2.4~2.5의 바닥과 연결해 본다.

#### 뮤텍스(Mutex) - "한 번에 딱 한 명"

- 화장실 문 하나에 달린 자물쇠. 들어간 사람이 잠그고 나오며 푼다.
- **소유권 개념:** **잠근 사람만 풀 수 있다.**
- 용도: 순수한 상호 배제.
- **바닥과 연결:** 실제 구현은 2.4의 하이브리드(fast path=CAS 한 번, slow path=futex)이고, 잠금·해제에 acquire·release 배리어(2.5)가 박혀 있어 가시성·순서까지 보장한다.

#### 세마포어(Semaphore) - "동시에 N명까지 / 신호용"

- 주차장 입구 "남은 자리 5" 전광판. 들어가면 4, 나오면 5, 0이면 대기.
- **소유권 없음:** 들어간 사람이 아닌 다른 쪽이 풀 수도 있다.
- 이진(N=1)/카운팅(N개) 두 종류.
- **내부 구현:** = **정수 카운터 + 대기 큐**. `P/wait`은 카운터를 원자적으로 감소, 음수면 자신을 큐에 넣고 잠든다. `V/signal`은 증가시키고 대기자가 있으면 하나 깨운다. (감소·큐 삽입 자체가 원자적이어야 해 내부에 원자 명령/스핀락을 씀.)

**생산자-소비자를 세마포어 3개로**

```
empty = N   // 빈 칸 수
full  = 0   // 찬 칸 수
mutex = 1   // 버퍼 보호

생산자:                     소비자:
P(empty)  // 빈 칸 확보      P(full)   // 찬 칸 확보
P(mutex)                    P(mutex)
 버퍼에 삽입                 버퍼에서 꺼냄
V(mutex)                    V(mutex)
V(full)   // 찬 칸 +1        V(empty)  // 빈 칸 +1
```

`P(mutex)`와 `P(empty)`의 **순서를 바꾸면 교착**이다. 생산자가 `P(mutex)`로 버퍼를 잠근 채 `P(empty)`에서 빈 칸을 기다리는데, 그 빈 칸은 소비자가 만들어야 하고 소비자는 `P(mutex)`에서 막힌다. **"자원 세마포어를 먼저, 상호배제 뮤텍스를 나중에"** 가 규칙(→ 2.7 교착 4조건과 직결).

**이진 세마포어 ≠ 뮤텍스:** 카운터 1이라 뮤텍스처럼 보이지만 **소유권이 없다**. 그래서 "A가 P, B가 V"가 가능 → **한쪽이 신호 보내고 다른 쪽이 받는** 용도엔 세마포어가, 순수 상호 배제엔 뮤텍스가 맞다.

#### 모니터(Monitor)와 조건 변수(Condition Variable)

- 모니터 = 언어 차원에서 상호 배제를 **자동 보장**하는 고수준 추상화(예: Java `synchronized`).
- 조건 변수 = "특정 조건이 될 때까지 대기, 되면 깨우기"(`wait`/`signal`). 보통 락과 함께 쓴다.

**왜 `if`가 아니라 `while`인가 - Mesa vs Hoare.** 이게 진짜 지식이다. 답은 조건 변수의 **의미론**에 있다.

- **Hoare 의미론**: `signal`하면 **즉시** 제어가 대기자에게 넘어가고 신호 보낸 쪽은 양보. 대기자가 깨어난 순간 조건이 **참임이 보장** → 이론상 `if`로 충분. 하지만 엄격한 제어 이양이 필요해 **거의 구현 안 됨**.
- **Mesa 의미론**(Lampson & Redell): `signal`은 **"이제 조건이 참일 수도 있다"는 힌트**일 뿐. 깨워진 대기자는 즉시 실행이 아니라 준비 큐로 가 **나중에 락을 다시 두고 경쟁**한다. 그 사이 **다른 스레드가 먼저 들어와 조건을 도로 거짓**으로 만들 수 있다.

현실의 거의 모든 시스템(Java·pthreads·Python)이 **Mesa**다. 그래서 깨어난 뒤 **조건을 반드시 다시 확인(`while`)** 해야 한다. pthreads는 여기 더해 **가짜 기상(spurious wakeup)** 까지 허용하므로 `while`은 절대 규칙:

```
lock();
while (!condition)          // ← if가 아니라 while
    cond_wait(&cv, &lock);
// 이 지점에서 condition은 확실히 참
unlock();
```

- **signal vs broadcast:** 조건이 여러 대기자를 만족시키거나 누굴 깨울지 애매하면 전부 깨움(단 **thundering herd** 주의 — 다 깨어나 하나만 이기고 도로 잠듦).
- **유실 기상(lost wakeup):** 락을 안 쥐고 signal하거나 wait 전에 signal이 지나가면 신호를 영영 놓침 → **조건 검사와 wait를 같은 락 아래** 두는 이유.

#### 스핀락(Spinlock)

- 재우지 않고 **계속 돌며(busy-wait)** 락을 노림. 아주 짧게 잡을 때만 유리(전환 비용 < 대기 비용). 구현·개선은 2.4(TAS→TTAS→티켓락) 참고.

#### 뮤텍스 vs 세마포어 한 줄 비교

> **뮤텍스 = 상호 배제(한 명)에 특화된 잠금 (소유권 O)** / **세마포어 = 자원 개수를 세는 더 일반적인 신호 장치 (소유권 X)**. 이진 세마포어는 뮤텍스와 비슷해 보이지만 소유권 유무에서 갈린다.

### 2.7 부작용 - 교착 상태(Deadlock)

- **교착 상태는 도구가 아니다. 도구(뮤텍스·세마포어)를 잘못 써서 생기는 _고장 상황_이다.**
- 정의: **서로가 가진 락을 영원히 기다리며 둘 다 멈춤.**
    - 예) A가 락1 쥐고 락2 기다림 + B가 락2 쥐고 락1 기다림 → 영원히 안 풀림.
    - 대표 예제: **식사하는 철학자 문제**.
- 발생 4조건(모두 충족 시): **상호 배제 · 점유 대기(Hold and Wait) · 비선점(No Preemption) · 순환 대기(Circular Wait)**.

**자원 할당 그래프(RAG)로 보기.** 프로세스·자원을 노드로, 요청/할당을 엣지로 그린다.

- 자원이 **인스턴스 1개씩**이면 **사이클 ⇔ 교착**.
- **여러 인스턴스**면 사이클은 **필요조건일 뿐**(사이클이 있어도 교착이 아닐 수 있음).

**4조건과 예방의 대응** (조건 하나만 깨면 교착은 안 생긴다):

|조건|깨는 방법(예방)|현실성|
|---|---|---|
|상호 배제|공유 가능 자원으로(읽기 전용)|대개 불가|
|점유 대기|필요한 락을 한 번에 다 잡거나, 없으면 다 놓기|자원 활용률↓|
|비선점|못 잡으면 가진 것도 뺏김(타임아웃)|**실무 애용**|
|순환 대기|**락에 전역 순서 부여, 항상 오름차순 획득**|**실무 1순위**|

**회피 vs 탐지**

- **회피 = 은행원 알고리즘**: `Max/Allocation/Available`로 **안전 순서(safe sequence)**가 존재하는 요청만 허용. 최대 요구량을 미리 알아야 하고 비용이 커 **실무엔 거의 없음**.
- **탐지·회복**: 주기적으로 **wait-for 그래프**의 사이클을 찾아 victim을 골라 롤백. **DB가 이 방식** — 교착을 0으로 만들기보다 "터지면 재시도"로 다룬다.

### 2.8 그 외 문제 + 올바름의 언어

**교착의 친척들**

- **기아(Starvation):** 특정 스레드가 계속 자원을 못 받음. (fair 락은 안전하지만 느림 — 트레이드오프.)
- **라이브락(Livelock):** 상태는 바뀌는데 진행이 없음(서로 양보만 반복). 지터 있는 백오프로 깬다.
- **우선순위 역전(Priority Inversion):** 낮은 우선순위가 자원을 쥐고 높은 우선순위를 막음. 해법은 우선순위 상속.

**동기화 코드를 평가하는 어휘** (면접·논문에서 그대로 쓰인다)

- **안전성(Safety):** "**나쁜 일이 절대 안 일어난다**." 예) 두 스레드가 동시에 임계구역에 없다(상호 배제).
- **활성(Liveness):** "**좋은 일이 결국 일어난다**." 예) 들어가려는 스레드는 언젠가 들어간다(진행·기아 없음). 교착 없음·기아 없음은 활성, 상호 배제는 안전 — **둘은 자주 상충**한다.

**진행 보장 계층 (lock-free의 세계)**

- **블로킹(blocking):** 한 스레드가 멈추면 다른 스레드도 막힐 수 있음(일반 락).
- **obstruction-free:** 혼자 돌면 끝난다.
- **lock-free:** 시스템 전체로는 **항상 누군가 진행**(개별 스레드는 기아 가능).
- **wait-free:** **모든 스레드가 유한 스텝 내 완료**. 가장 강하고 가장 어렵다.

**선형화 가능성(Linearizability):** 동시 자료구조 올바름의 기준. **각 연산이 호출~반환 사이 어느 한 순간에 원자적으로 일어난 것처럼** 보이고, 그 순간들의 순서가 실제 시간 순서를 존중하면 선형화 가능. "이 lock-free 큐가 맞나?"의 판정 잣대.

**ABA 문제 (CAS의 함정):** CAS가 값이 `A`인 걸 보고 성공시키지만 그 사이 `A→B→A`로 바뀌었을 수 있다(포인터 재사용 등). 값은 같아도 상태는 다름 → 잘못된 성공. 해결: 버전 태그 붙인 포인터, hazard pointer, epoch-based reclamation. lock-free 구현의 대표 난관.

### 2.10 동기화 심화, 한 장 요약

```
소프트웨어만으로는 상호배제가 불안정 (Peterson도 재배치에 깨짐)
        │
        ▼
하드웨어 원자 명령(TAS/CAS/FAA)이 진짜 바닥
        │  └ 스핀락 → TTAS → 티켓락(공정) → futex(스핀+재우기)
        ▼
메모리 모델: 원자성 ≠ 가시성 ≠ 순서
        │  └ 재배치는 정상 · 배리어(acquire/release)가 happens-before를 만듦
        │  └ 락이 "안전한" 진짜 이유 = 라이브러리가 배리어를 심어서
        ▼
고수준 도구: 세마포어(카운터+큐, P순서 주의) · 모니터(Mesa라서 while 필수)
        │
        ▼
교착: RAG 사이클 · 4조건별 예방 · 은행원(이론) vs 탐지·회복(DB)
        │
        ▼
올바름의 언어: safety/liveness · 진행보장(wait-free>lock-free) · 선형화 · ABA
```

**한 문장:** 동기화의 깊이는 "락을 쓴다"가 아니라, **하드웨어 원자 명령 위에 메모리 배리어로 가시성·순서를 세우고, 그 위에 세마포어·모니터를 얹되 각자의 의미론(P 순서, Mesa `while`)을 지키는 일**이다.

## 3. 오늘날 어떻게 적용되나

> **1~2의 도구를 "서버 한 대가 수만 연결을 감당한다"는 극한에 욱여넣을 때 벌어지는 일**이다.

### 3.1 C10K 문제

- 웹이 커지며 서버 한 대가 수만 명을 동시에 상대해야 하는 시대.
- thread-per-connection을 그대로 적용 → 연결 1만 = 스레드 1만.
- **수학:** 스레드당 스택 1MB × 1만 = **10GB**. 연결 유지만으로 메모리 거덜. + 1만 개 컨텍스트 스위칭으로 CPU가 "전환"에 시간 낭비.
- 1999년 Dan Kegel이 던진 "동시 1만 연결" 화두가 **C10K**. 지금은 해결됐고 한 대로 수백만(C10M)을 노린다.
- **붕괴의 본질:** 1만 연결 중 대부분은 그 순간 **아무 일도 안 하고** 다음 요청을 기다리며 열려만 있다. 그런데도 각자 **무거운 OS 스레드 하나**를 붙잡고 있다. → **"대기 중인 연결"과 "비싼 실행 자원"을 1:1로 묶은 게 낭비.** 모든 해법은 이 묶음을 끊는다.

### 3.2 해결 1단계 - 논블로킹 I/O

- `read()`가 데이터 없을 때 멈추지 말고 **"아직 없음(EAGAIN)"을 즉시 반환**하게.
- 스레드가 안 멈추니 한 스레드가 여러 소켓을 돌며 확인 가능.
- **문제:** 1만 개를 무한 루프로 "준비됐어?" 일일이 물으면 대부분 "아직"인데도 CPU 100% 소모 → **바쁜 대기(busy polling)**. → "내가 묻지 말고, 준비되면 **커널이 알려주게**"로 진화.

### 3.3 해결 2단계 - 이벤트 다중화 (select → poll → epoll → io_uring)

> 핵심 전환: **"내가 1만 개 확인" → "커널에 맡겨두고 준비된 것만 통지받기".** 역사가 곧 최적화의 역사.

|단계|동작|한계/특징|
|---|---|---|
|**select / poll**|"이 fd들 중 준비된 거?" 매번 전체 목록을 커널에 넘김|연결 수에 비례해 느림 O(n)|
|**epoll** (Linux)|관심 fd를 커널에 **한 번 등록**, 커널이 내부 트리로 관리하다 **준비된 것만** 반환|대기 비용이 준비된 개수에만 비례. nginx·Redis·Node의 비결. 단, **실제 read/write는 여전히 내가** → 이벤트당 최소 2회 syscall|
|**io_uring** (2019~)|"가능할 때 통지(readiness)"가 아니라 **"대신 해주고 끝나면 통지(completion)"**. 공유 링 버퍼(제출/완료 큐)로 요청·결과를 일괄 처리|syscall 횟수 급감. 단, 배칭·버퍼 등록 등 특성에 맞춰 설계해야 실이득|

> 한 문장: **"내가 묻기" → "커널이 가능 여부 통지(epoll)" → "커널이 일까지 하고 완료 통지(io_uring)".** 일을 점점 커널로 떠넘기는 진화.

### 3.4 이벤트 루프 

- 구조는 단순: 무한 루프에서 ① "준비된 이벤트?" 묻고(`epoll_wait`) ② 준비된 fd들의 콜백 실행 ③ 다시 ①. **단 하나의 스레드**가 수천 연결을 한 바퀴씩 처리.
- **제1계명: "이벤트 루프를 절대 블로킹하지 마라."** 콜백 하나가 무거운 계산/블로킹으로 1초 잡으면 그 1초간 나머지 수천 연결이 전부 멈춘다(스레드가 하나니까). → Node에서 동기 함수 기피가 목숨 규칙인 이유. CPU 무거운 일은 별도 스레드 풀로.

### 3.5 새 문제와 해법 - 콜백 지옥 → async/await

- 이벤트 루프는 효율적이지만 "끝나면 → 이거 → 끝나면 → 저거"를 콜백으로 엮어 **콜백 지옥**이 됨. 순차적 일을 순차적으로 못 씀.
- **async/await의 아이디어:** _동기 코드처럼 위에서 아래로 읽히게 쓰되, 컴파일러가 이벤트 루프가 굴릴 형태로 자동 변환._
- 그 변환의 정체 = **상태 머신.** `await`가 있는 함수를 컴파일러가 잘게 쪼개, 각 `await`를 "여기서 멈췄다 나중에 재개"하는 상태로 만든다. 진행 위치(상태 번호)와 지역 변수를 구조체에 저장, `poll`이 불릴 때마다 한 칸 전진하다 끝나면 완료 반환.
- **OS와의 다리:** 1.3의 "OS 스케줄러가 블로킹 스레드를 재웠다 깨우는" 일을, async/await는 **유저공간에서 작업 단위로 흉내** 낸다. `await`에서 멈추고(상태 저장), I/O가 준비되면 실행기(executor)가 다시 `poll`해 깨운다. OS 스레드를 통째로 재우지 않고 **가벼운 "작업"만** 멈췄다 깨우니 전환 비용이 거의 없다. → **async 런타임 = 사실상 유저레벨 스케줄러.** (epoll이 "준비" 신호를 주면 런타임이 멈춘 작업을 깨움)
- 참고: Rust의 Future는 **lazy** — `await` 전엔 아무 일도 안 함(JS Promise는 즉시 실행). "future 만들고 await 안 함"이 흔한 버그.

### 3.6 또 다른 길 - 경량 스레드 (M:N): 고루틴, 가상 스레드

- async/await의 대가: 함수가 sync/async로 갈라지고 코드 전체가 async에 물듦(**함수 색칠 문제**).
- 다른 학파: **"개발자는 그냥 스레드처럼 짜게 두고, 런타임이 알아서 싸게."**
- **M:N 모델:** 가벼운 유저레벨 단위 수백만 개를 소수의 OS 스레드 위에 얹어 런타임이 스케줄링. 블로킹 만나면 그 가벼운 단위만 빼두고(스택을 힙에 저장) 다른 작업을 올림. 개발자 눈엔 평범한 블로킹 코드인데 논블로킹처럼 돈다.
    - **Go 고루틴:** 언어에 M:N 스케줄러 내장. `go f()` 한 줄로 수십만 개.
    - **Java 가상 스레드(Project Loom, JDK 21+):** 스택을 힙에 저장 → footprint가 MB가 아니라 수백 바이트. "연결마다 스레드 하나"라는 옛 안티패턴을 실용적 기본값으로 부활. 블로킹 코드를 그냥 써도 수십만 연결. reactive의 복잡함을 상당 부분 대체.
- **두 갈래 정리:** **async/await**(멈출 지점을 명시 — Rust·JS·Python) vs **경량 스레드**(런타임이 투명 처리 — Go·Java Loom). 목표는 같다 — "대기 중 연결"을 "비싼 OS 스레드"에서 떼어내기.

### 3.7 그래도 안 사라지는 것 - 동기화

- **착각 주의: "async면 락이 필요 없다"는 거짓.** 2장의 공유 자원 문제는 그대로 살아남고, 오히려 더 미묘해진다.
- 백엔드의 공유 가변 상태: **커넥션 풀, 캐시, 레이트 리미터, 카운터·통계** — 여러 작업이 동시에 건드리니 여전히 보호 필요.
- **2장과의 연결:** 커넥션 풀이 곧 **카운팅 세마포어**(2.6)다. "커넥션 10개"는 "동시 DB 작업 10개까지, 11번째는 대기". 외부 API 동시 호출 제한도 같은 패턴.
- async 특유의 함정: **"await 너머로 락을 들고 가지 마라."** `await`에서 멈추면 같은 스레드에 다른 작업이 올라오는데, 그때까지 락을 쥐면 데드락/심각한 경합. → **async-aware 락**(예: Rust `tokio::sync::Mutex`)은 await 동안 스레드를 막지 않고 양보하도록 설계됨.

### 3.8 운영에서 새로 터지는 것 - 백프레셔, 취소

- **백프레셔(Backpressure):** 가장 과소평가됨. 유입 속도 > 처리 속도면 큐가 무한정 자라 OOM으로 죽음. "감당 못 하면 받는 속도를 늦추거나 거절"하는 흐름 제어 필수. (2.6 생산자-소비자가 굳이 **유한** 버퍼를 다루는 실무적 이유가 이것.)
- **취소·타임아웃 전파 / 구조적 동시성:** 요청이 끊기거나 타임아웃 시 그 요청이 만든 하위 작업(DB 쿼리, 외부 API)도 함께 멈춰야 좀비 작업이 안 생김. **구조적 동시성(structured concurrency)** = "부모 작업이 끝나거나 실패하면 자식 작업도 함께 정리"(Java `StructuredTaskScope`, Kotlin 코루틴 등). 옛 fire-and-forget 스레드의 누수를 구조적으로 막는다.

## 4. 정리

### 4.1 전체를 한 문장으로

> **CPU와 I/O의 속도 불균형** → OS가 스레드·스케줄러·블로킹 I/O·락이라는 **도구함**을 줌 → "서버 한 대, 수만 연결"에서 thread-per-connection이 **C10K로 붕괴** → "대기 중 연결 ↔ 비싼 OS 스레드"의 1:1을 끊는 게 해법 → **논블로킹 I/O + epoll/io_uring으로 한 스레드가 수천 연결 감시** → **이벤트 루프** → 코드가 더러워지니 **async/await(유저레벨 스케줄러)** 또는 **경량 스레드(M:N)** → 그래도 **공유 상태·동기화는 살아남고**, 운영에선 **백프레셔·취소**가 새로 등장.

### 4.2 동기화만 따로 한 문장으로

> "락을 쓴다"의 실체는 → **하드웨어 원자 명령(TAS/CAS/FAA) 위에**, **메모리 배리어(acquire/release)로 가시성·순서를 세우고**, 그 위에 세마포어·모니터를 얹되 **각자의 의미론(세마포어 P 순서, 모니터 Mesa `while`)을 지키는 일** → 잘못 쓰면 **교착**, 이를 다스리는 언어가 **safety/liveness·진행 보장·선형화**다.
