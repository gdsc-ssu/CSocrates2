#  CFS는 왜 퇴장했는가

> [!info] 학습 목표
> 
> - CFS가 가진 구조적 한계를 이해한다
> - EEVDF의 핵심 개념(virtual time, lag, virtual deadline)을 설명할 수 있다
> - 지금 내 컴퓨터가 실제로 EEVDF를 쓰고 있는지 확인할 수 있다

---

## 0. 들어가기 전에 
> [!question] "지금 우리 노트북/서버 커널, CFS 쓰고 있을까요?" → 정답: **아니요.** Linux 6.6 (2023년 10월) 부터 **EEVDF**가 기본 스케줄러로 바뀌었습니다.

10년 넘게 "공평한 스케줄러 = CFS"라고 배웠는데, 정작 지금 거의 모든 최신 배포판은 CFS를 쓰지 않는다.

# 1. CFS

![[스크린샷 2026-06-29 오후 7.50.08.png]]

프로세스를 선택하는 방법엔 정말 복잡하고 멋있는 알고리즘이 있다. 
각각의 프로세스는 우선 순위(ex nice 값)가 있는데 이 우선 순위는 virtual clock 으로 부터 정해진다 


## 1-1. Fairneness

CPU 스케줄링을 생각했을 때 가장 먼저 떠올려야될 개념, 철학은 공정성입니다. 

"모든 작업에 CPU 를 정확히 동일하게 부여하자"
하지만 이렇게 단순하게 생각을 하면 엄청나게 비효율적입니다. 중요한 작업이 중요하지 않은 작업과 똑 같은 시간을 할당 받게 되면 프로그램이 원할하게 돌아가지 못할 것 입니다. 그래서 리눅스는 ==**가중** 공정성 모델== 을 사용합니다. 

목표는 단순히 평등만이 아닙니다. 모든 업무가 공평하게 분배 되는 것이고 그 비중은 "중요도"에 따라 가중치가 부여됩니다. 

이 보든 것을 가능하게 하는 것이 CFS(Completely Fair Scheduler) 입니다. 완전이 들어가는 것만 봐도 얼마나 공정할지 감도 안잡힙니다.

리눅스 시스템에서 실행되는 거의 모든 일반적인 프로세스는 CFS가 모든 것을 제어합니다. 
## 1-2 Vruntime

CPU 는 가상 런타임이라고 하는 스톱워치를 사용합니다. 
가상 런타임을 이해하는 가장 쉬운 방법은 공정성의 "부채"와 같다고 생각하시면 됩니다. 실시간으로 중요도, 가중치를 추적하는 것이 아니라 가중치가 적용된 가상 시간을 추적합니다. 


![[스크린샷 2026-06-29 오후 8.31.08.png]]

1. 스케줄러는 항상 가상 런타임이 가장 짧은 작업을 선택합니다. 
2. 해당 작업이 실행되면 가상 런타임과 공정성의 부채가 증가합니다. 
3. nice 값이 작았던 고우선순위의 작업은 VR 런타임을 느리게 누적 시킵니다 -> 더 오래 점유할 수 있게 하기 위함 

```
vruntime += delta_exec / weight
```

![[스크린샷 2026-06-30 오후 12.59.00.png]]

CFS의 아이디어: 모든 프로세스의 `vruntime`(가상 실행시간)을 추적해서, **vruntime이 가장 작은 프로세스**를 다음에 실행시킨다. 즉 "덜 뛴 애를 먼저 뛰게 한다."


## 1-3 Runqueue


![[스크린샷 2026-06-30 오후 1.00.00.png]]

- **정렬 기준:** `vruntime`이 **낮을수록 왼쪽**, **높을수록 오른쪽**에 위치합니다.
- **자가 균형:** 새로운 프로세스가 들어오거나 실행을 마친 프로세스가 다시 트리에 추가될 때, 트리가 한쪽으로 치우치지 않도록 스스로 회전(Rotation)하여 균형(레드-블랙 트리의 특징)을 유지합니다. 덕분에 삽입/삭제가 의 성능을 보장합니다.
- **`rb_leftmost` 캐싱:** 리눅스 커널은 트리의 가장 왼쪽 하단에 있는 노드(그림의 **P1, 10ms**)의 주소를 별도로 캐싱해둡니다. 덕분에 다음에 실행할 프로세스를 찾을 때는 트리를 뒤지지 않고  만에 바로 꺼내옵니다.


### CFS 한계, "공정함"이 곧 "빠른 응답"은 아니다

> [!question] 생각해볼 질문 프로세스 2개가 경쟁할 때와, 프로세스 200개가 경쟁할 때 — CFS는 둘 다 "공평"하다고 말할 수 있을까?

- 프로세스 2개: 각자 50%씩 받음 → 내 차례가 금방 돌아옴 → 체감 지연 거의 없음
- 프로세스 200개: 각자 0.5%씩 받음 → **여전히 수학적으로는 "공평"** 하지만, 한 바퀴 돌아서 내 차례가 다시 오기까지 걸리는 시간(레이턴시)은 확 길어짐

**CFS는 "CPU 시간을 비례적으로 공평하게 나눈다"는 것만 보장하지, "언제까지는 반드시 실행시켜준다"는 보장은 하지 않습니다.** 이게 구조적 약점, 즉 CFS의 아킬레스건입니다.

| 문제                | 설명                                                                   |
| ----------------- | -------------------------------------------------------------------- |
| 레이턴시 보장이 없음       | 부하(runnable 태스크 수)가 늘어날수록 "공평하게는 받지만 느리게 받는" 상황이 구조적으로 발생            |
| 휴리스틱 누적           | 이 문제를 패치마다 sleeper fairness 같은 휴리스틱으로 땜질 → 코드가 점점 복잡해지고 동작이 예측 불가능해짐 |
| `nice` 값의 의미가 흐릿함 | "얼마나 더 받을지"는 표현 가능해도 "언제까지 받아야 하는지(deadline)"는 표현할 방법이 없음            |

### low Contention

시스템의 부하가 적고 경쟁이 적은 경우는 CPU의 작업 목록인 실행 Queue는 가볍습니다. 스케줄러는 그중에서 가장 우선순위가 높은 작업을 선택하는데 시간이 오래걸리지 않죠 

### High Contention

시스템 부하가 많은 상황에서는 미세한 가상 런타임 차이로 선택을 못 받게 되면 어플리케이션 지연으로 이어지기 때문에 CPU 부하가 발생합니다. 


### 약점은 실제로 어떻게 드러나는가 → PSI로 측정

High Contention일 때, "공평하게 나누고는 있지만, 태스크들이 자기 차례를 기다리며 멈춰있는 시간"이 늘어납니다. 이 증상을 정량적으로 측정하는 커널 지표가 바로 **PSI(Pressure Stall Information)** 입니다.


![[스크린샷 2026-06-30 오전 10.12.30.png]]
커널은 이때 발생하는 정체 시간을 PSI(Pressure Stall Information) 라는 수치로 정확하게 측정하며
기존에 쓰던 CPU 사용률(`%util`)이나 `load average` 같은 지표는 "리소스가 얼마나 바쁜지"는 보여주지만, **"그 리소스 부족 때문에 작업이 실제로 얼마나 지연되고 있는지"** 는 보여주지 못합니다.

 PSI는 "태스크들이 리소스를 못 구해서 멈춰있는(stall) 시간의 비율"을 직접 측정하며 세 가지 리소스(CPU, 메모리, I/O)에 대해 각각 측정을 합니다. 
```
/proc/pressure/cpu
/proc/pressure/memory
/proc/pressure/io
```


```
memory
some avg10=25.00 avg60=10.00 avg300=2.00 total=8500000
full avg10=12.00 avg60=5.00  avg300=1.00 total=4200000
```
- **`some`**: 적어도 한 태스크가 해당 리소스를 기다리느라 멈춘 시간의 비율 
- **`full`**: **모든** 실행 가능한 태스크가 동시에 멈춰서 CPU가 완전히 놀고 있는 시간의 비율 
- **`avg10/60/300`**: 최근 10초/60초/300초 동안의 평균 stall 비율 (%)
- **`total`**: 부팅 이후 누적 stall 시간 (마이크로초)

해석
- 최근 10초 동안 전체 시간의 25%는 **적어도 한 프로세스**가 메모리 부족으로 멈춰있었다 (`some`)
- 그중 12%는 **모든** 실행 가능한 프로세스가 동시에 멈춰서 시스템 전체가 정지 상태였다 (`full`) → 이건 꽤 심각한 신호
- `avg300`은 2%/1%로 낮음 → 즉, **최근 들어 갑자기 압박이 심해진 것** (avg10 > avg60 > avg300 순으로 증가하는 추세)


`some` vs `full`을 같이 봐야 하는 이유

```
some avg10=40.00
full avg10=2.00
```
-> "한 태스크는 자주 멈추는데, 시스템 전체가 멈추는 일은 거의 없다" = **일부 프로세스만 압박받는 중** (예: 메모리 많이 먹는 프로세스 하나가 경합 중이고, 나머지는 잘 돌아감). 전체 시스템 장애 위험은 낮음.


```
some avg10=40.00 
full avg10=35.00
```

→ "거의 모든 시간에 시스템 전체가 멈춰있다" = **시스템 전체가 리소스 고갈 직전**. 이건 즉시 조치가 필요한 신호 (메모리 증설, OOM 발생 임박 등).

이 둘의 **차이(gap)** 가 클수록 "소수 프로세스 문제", 차이가 작을수록 "시스템 전체 문제"라고 해석할 수 있습니다.

이러한 PSI 를 확인하면 CFS의 구조적 한계가 보이는데요

**CFS의 구조적 한계:**

| 문제                | 설명                                                                           |
| ----------------- | ---------------------------------------------------------------------------- |
| 레이턴시 보장이 약함       | "공평한 분배"만 신경 쓰다 보니, 지금 당장 빨리 응답해야 하는 태스크(오디오, 인터럽트 핸들러 등)를 우선시할 명확한 메커니즘이 없음 |
| 휴리스틱 누적           | 레이턴시 문제를 패치마다 휴리스틱(sleeper fairness 등)으로 땜질 → 코드가 점점 복잡해지고 예측 불가능해짐          |
| `nice` 값의 의미가 흐릿함 | "얼마나 더 받을지"는 알아도 "언제까지 받아야 하는지"에 대한 개념이 없음                                   |

> [!tip]  CFS도 "Completely **Fair**"인데, 왜 레이턴시 문제가 생겼을까? → 공평함(fairness)과 응답성(latency)은 다른 축의 문제라는 게 핵심.

## 2. EEVDF 

"마감일 설정"

EEVDF = **Earliest Eligible Virtual Deadline First**. 사실 1995년 논문에서 나온 알고리즘인데, Peter Zijlstra가 2023년에 Linux 커널용으로 구현해서 6.6에 머지했습니다.

![[스크린샷 2026-06-30 오후 2.22.00.png]]

### 2-1. Virtual Time과 Lag

- 모든 태스크는 **가상 실행시간(virtual runtime)** 을 가진다 (CFS의 vruntime과 유사하지만 계산 방식이 다름)
- **Lag** = "이 태스크가 받아야 할 CPU 시간 − 실제로 받은 CPU 시간"
    - Lag ≥ 0 → 아직 못 받은 몫이 있음 → **eligible(자격 있음)**
    - Lag < 0 → 이미 자기 몫보다 더 받음 → **ineligible**

Lag는 작업이 할당된 몫보다 얼마나 뒤쳐져 있는지를 나타냅니다.

> [!note] 핵심 CFS는 "vruntime이 작은 애 = 다음 차례"였지만, EEVDF는 "**eligible한 애들 중에서만** 고른다"는 자격 검증 단계가 먼저 있다.

### 2-2. Virtual Deadline

 "eligible에서 단순히 가장 뒤쳐진 것을 고르지 않는다"

eligible한 태스크들 중에서, 각 태스크의 **virtual deadline(VD)** 을 계산:

```
VD = (eligible해진 시점의 가상시간) + (요청한 타임슬라이스 / weight)
```

- weight는 `nice` 값에서 변환된 우선순위 가중치 (nice가 낮을수록 weight 큼)
- **VD가 가장 빠른(earliest) 태스크를 다음에 실행** → 이름 그대로 "Earliest Eligible Virtual Deadline First"

### 2-3.  예시

태스크 X(인터랙티브, 짧은 작업)와 태스크 Y(배치, 긴 작업)가 있다고 해봅시다. 둘 다 weight는 같음(nice 0).

vruntime은 정의상 "**지금까지 실제로 받은 CPU 시간을 weight로 나눈 값**"입니다. weight가 같으니(둘 다 nice 0, weight=1) vruntime은 그냥 누적 실행시간 그 자체가 되는 상황으로 예시를 살펴 보겠습니다.

| 태스크       | 지금까지의 실행 이력                              | 누적 vruntime |
| --------- | ---------------------------------------- | ----------- |
| X (인터랙티브) | 직전까지 CPU를 100ms만큼 받았고, 방금 막 깨어나서 실행 대기 중 | **100**     |
| Y (배치)    | 지금까지 95ms 동안 CPU를 계속 점유하며 돌았음            | **95**      |

| 태스크 | 요청 타임슬라이스        | 특성              |
| --- | ---------------- | --------------- |
| X   | 2ms (짧음, 응답성 중요) | 막 깨어난 인터랙티브 태스크 |
| Y   | 20ms (긺, 처리량 중요) | CPU 집약적 배치 작업   |

**CFS라면**: vruntime이 더 작은 Y(95 < 100)를 무조건 먼저 실행. Y가 20ms를 다 쓸 때까지 X는 기다려야 함 → 인터랙티브 태스크인 X가 불필요하게 오래 대기.

**EEVDF라면**: virtual deadline을 계산.

```
VD(X) = 100 + 2/1 = 102
VD(Y) = 95 + 20/1 = 115
```

→ X의 deadline(102)이 Y의 deadline(115)보다 빠름 → **X가 먼저 실행됨**, Y가 약간 더 기다림.


### 2-4. Latency-nice

EEVDF는 `nice`(CPU 점유율 우선순위) 와 별개로 **`latency-nice`** 라는 개념도 도입해, "이 태스크는 CPU를 많이 안 써도 되지만 빨리 응답은 받아야 한다"는 걸 별도로 표현할 수 있게 함. (예: 인터랙티브 앱 vs 백그라운드 배치 작업)

## 3. CFS vs EEVDF 비교

| 항목         | CFS              | EEVDF                           |
| ---------- | ---------------- | ------------------------------- |
| 선택 기준      | vruntime 최소값     | eligible 태스크 중 VD 최솟값           |
| 레이턴시 보장    | 휴리스틱 의존          | deadline 메커니즘으로 구조적 보장          |
| 우선순위/지연 분리 | `nice` 하나로 처리    | `nice` + `latency-nice` 분리      |
| 알고리즘 기원    | CFS 자체 설계 (2007) | 1995년 학술 논문 기반                  |
| 적용 시점      | ~2007년 도입        | 커널 6.6 (2023) 도입, 이후 기본값으로 자리잡음 |
