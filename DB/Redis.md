### 정의
레디스(Redis)는 메모리 기반의 데이터 저장소이다. 
키-밸류(key-value) 데이터 구조에 기반한 다양한 형태의 자료 구조를 제공하며, 데이터들을 저장할 수 있는 저장소이다. 

**key-value** **구조** 데이터란, mysql 같은 관계형 데이터가 아닌 비 관계형 구조로서 데이터를 그저 '키-값' 형태로 단순하게 저장하는 구조를 말한다. 그래서 관계형 데이터베이스와 같이 쿼리 연산을 지원하지 않지만, 대신 데이터의 **고속 읽기와 쓰기에 최적화** 되어 있다. 그래서 Redis는 일종의 **NoSQL 로 분류**되기도 한다.
![[Pasted image 20260511225358.png]]

##### NoSQL?
NoSQL은 Not Only SQL의 약자로써 기존 관계형 데이터베이스(RDBMS)보다 더 융통성 있는 데이터 모델을 사용하고 데이터의 저장 및 검색을 위한 특화된 메커니즘을 제공하는 데이터 저장기술을 의미한다.  
NoSQL 데이터베이스는 단순 검색 및 추가 작업에 있어서 매우 최적화된 키-값 저장 기법을 사용하여 응답속도나 처리 효율 등에 있어서 매우 뛰어난 성능을 보여준다.

##### NoSQL 특징
- RDBMS와 달리 데이터간의 관계를 정의하지 않는다.
- RDBMS에 비해 훨씬 더 대용량의 데이터를 저장할 수 있다.
- 반정형화, 비정형화된 데이터에 적합하다
- 분산형 구조이고 확장성이 뛰어나다
- 고정되지 않은 테이블 스키마를 가진다
- ACID 대신 Eventual Consistency 를 허용한다
    - Eventual Consistency → 다양한 기기에 분산 저장되있는 데이터를 Update 할 경우 실시간으로 다른 기기에 전파하기 어려운데 이 점을 조금 타협하여 최신은 아닐 수 있지만 Update 전까지는 최신의 데이터를 반환한다.


#### 왜 빠른가
Redis가 빠른 이유는 크게 두 가지다.

첫 번째는 메모리 기반이라는 점이다. 디스크 I/O가 없기 때문에 데이터 접근 속도가 마이크로초(μs) 단위로 나온다. 일반적인 RDB가 밀리초(ms) 단위인 것과 비교하면 수백 배 차이가 난다.

두 번째는 단일 스레드 이벤트 루프 구조다. 멀티스레드 환경에서는 동시성 문제를 해결하기 위해 락(Lock)을 걸고 푸는 오버헤드가 생긴다. Redis는 단일 스레드로 요청을 순서대로 처리하기 때문에 이 오버헤드가 없다. 대신 I/O 멀티플렉싱을 사용해 여러 클라이언트 요청을 동시에 처리하는 것처럼 동작한다.

#### 영속성 옵션 (RDB vs AOF)
Redis는 메모리 기반이라 서버가 꺼지면 데이터가 사라진다. 이를 보완하기 위해 두 가지 영속성 옵션을 제공한다.

**RDB(Redis Database**)는 특정 시점의 메모리 스냅샷을 디스크에 저장하는 방식이다. 예를 들어 "5분마다 저장", "1000건 변경될 때마다 저장" 같은 조건을 설정할 수 있다. 장점은 파일이 작고 복구가 빠르다는 것이고, 단점은 스냅샷 사이에 서버가 죽으면 그 사이 데이터는 유실된다는 것이다.

**AOF(Append Only File)** 는 Redis에 들어오는 모든 쓰기 명령을 로그 파일에 순서대로 기록하는 방식이다. 서버가 재시작되면 이 로그를 처음부터 재실행해서 데이터를 복구한다. 데이터 유실이 거의 없다는 게 장점이지만, 파일 크기가 커지고 복구 시간이 오래 걸린다는 단점이 있다.

실무에서는 두 가지를 함께 사용하는 경우가 많다. RDB로 빠른 복구를 챙기고, AOF로 데이터 유실 최소화를 챙기는 방식이다. 다만 Redis를 순수 캐시 용도로만 사용한다면 영속성 옵션을 아예 끄기도 한다. 어차피 캐시 데이터는 원본이 DB에 있기 때문이다.

![[Pasted image 20260519181549.png]]
- Redis를 캐시로만 사용하는 경우
- 백업은 필요하지만 어느 정도의 데이터 손실이 발생해도 괜찮은 경우
- 장애 상황 직전까지의 모든 데이터가 보장되어야 할 경우
- 제일 강력한 내구성이 필요한 경우


### 자료구조
Redis는 단순한 키-값 저장소처럼 보이지만, 값(Value)으로 다양한 자료구조를 지원한다. 어떤 자료구조를 쓰느냐에 따라 성능과 구현 방식이 크게 달라지기 때문에 각각의 특성을 잘 이해하는 게 중요하다.

##### String
가장 기본적인 자료구조로, 텍스트뿐만 아니라 숫자, JSON, 바이너리 데이터까지 저장할 수 있다. 최대 512MB까지 저장 가능하다.

```
SET user:1:name "김철수"
GET user:1:name  → "김철수"

SET stock:item:100 50      # 재고 50개
INCR stock:item:100        # 원자적으로 1 증가 → 51
DECR stock:item:100        # 원자적으로 1 감소 → 50
```

실무에서는 주로 캐시 데이터 저장, 카운터(조회수, 좋아요 수), 분산 락 구현에 사용된다. INCR/DECR 명령은 원자적으로 실행되기 때문에 동시에 여러 서버에서 요청이 와도 정확한 카운팅이 가능하다.

##### List
순서가 있는 문자열의 연결 리스트다. 앞(Left)과 뒤(Right) 양쪽에서 삽입/삭제가 가능하다.

```
LPUSH queue:email "mail1"   # 왼쪽에 삽입
RPUSH queue:email "mail2"   # 오른쪽에 삽입
RPOP queue:email            # 오른쪽에서 꺼냄 → "mail2"
LRANGE queue:email 0 -1     # 전체 조회
```

실무에서는 주로 작업 큐(Job Queue), 최근 본 상품 목록, 타임라인 피드 구현에 사용된다. LPUSH로 넣고 RPOP으로 꺼내면 FIFO 큐처럼 동작한다.

##### Set
중복을 허용하지 않는 순서 없는 집합이다. 집합 연산(합집합, 교집합, 차집합)을 지원한다.

```
SADD user:1:follow 2 3 4    # 유저1이 2,3,4를 팔로우
SADD user:2:follow 3 4 5    # 유저2가 3,4,5를 팔로우
SINTER user:1:follow user:2:follow  # 교집합 → {3, 4} (공통 팔로우)
SUNION user:1:follow user:2:follow  # 합집합 → {2, 3, 4, 5}
```

실무에서는 태그 시스템, 좋아요/팔로우 목록, 중복 방문 체크 등에 사용된다. 특히 집합 연산을 활용해 "공통 친구", "같은 태그를 가진 게시물" 같은 기능을 빠르게 구현할 수 있다.

##### Sorted Set
Set에 score(점수)를 추가한 자료구조다. score를 기준으로 자동 정렬된다.

```
ZADD ranking 1500 "userA"
ZADD ranking 3200 "userB"
ZADD ranking 2800 "userC"
ZRANGE ranking 0 -1 WITHSCORES   # 오름차순 전체 조회
ZREVRANGE ranking 0 2 WITHSCORES  # 내림차순 상위 3명
ZRANK ranking "userA"             # userA의 순위 조회
```

실무에서는 실시간 랭킹 시스템, 우선순위 큐, 시간 기반 이벤트 스케줄링에 사용된다. 게임 리더보드나 검색어 자동완성 기능에서 자주 볼 수 있다.

##### Hash
하나의 키 안에 필드-값 쌍을 여러 개 저장하는 구조다. 객체를 표현하기에 적합하다.

```
HSET user:1 name "김철수" age "28" city "서울"
HGET user:1 name        → "김철수"
HGETALL user:1          → name, 김철수, age, 28, city, 서울
HINCRBY user:1 age 1    → 29 (원자적 증가)
```

실무에서는 사용자 프로필, 상품 정보, 설정값 저장 등 여러 필드를 가진 객체를 저장할 때 사용한다. JSON 문자열로 저장하는 것보다 특정 필드만 수정하거나 조회하는 게 훨씬 효율적이다.


### 캐시 전략

##### Cache-Aside (Lazy Loading)
가장 일반적으로 사용되는 캐시 전략이다. 애플리케이션이 직접 캐시와 DB를 제어한다.

동작 방식은 이렇다. 데이터를 요청하면 먼저 캐시를 확인한다. 캐시에 데이터가 있으면(Cache Hit) 그대로 반환한다. 없으면(Cache Miss) DB에서 조회한 뒤 캐시에 저장하고 반환한다.

```
def get_user(user_id):
    # 1. 캐시 확인
    cached = redis.get(f"user:{user_id}")
    if cached:
        return cached  # Cache Hit

    # 2. DB 조회
    user = db.query(f"SELECT * FROM users WHERE id = {user_id}")

    # 3. 캐시에 저장 (TTL 1시간)
    redis.setex(f"user:{user_id}", 3600, user)
    return user
```

장점은 실제로 필요한 데이터만 캐시에 올라간다는 것이고, 단점은 첫 요청은 항상 Cache Miss가 발생해서 느리다는 것이다. 이를 보완하기 위해 서버 시작 시 자주 쓰는 데이터를 미리 캐시에 올려두는 Cache Warming을 하기도 한다.

##### Write-Through
데이터를 쓸 때 캐시와 DB에 동시에 저장하는 전략이다.

```
def update_user(user_id, data):
    # 1. DB 저장
    db.query(f"UPDATE users SET ... WHERE id = {user_id}")

    # 2. 캐시도 동시에 갱신
    redis.setex(f"user:{user_id}", 3600, data)
```

장점은 캐시와 DB가 항상 일치한다는 것이다. 단점은 쓰기 요청마다 두 곳에 저장하니 쓰기 속도가 느려지고, 한 번도 읽히지 않을 데이터도 캐시에 올라가는 낭비가 생긴다.

##### Write-Behind (Write-Back)
캐시에 먼저 저장하고, DB에는 나중에 비동기로 저장하는 전략이다. 쓰기 성능이 가장 빠르지만, 캐시가 죽으면 아직 DB에 반영되지 않은 데이터가 유실될 위험이 있다. 실무에서는 로그 수집, 좋아요 수 집계처럼 약간의 데이터 유실이 허용되는 경우에 제한적으로 사용한다.

#### TTL과 캐시 만료 전략
TTL(Time To Live)은 캐시 데이터의 유효 시간이다. TTL이 지나면 Redis가 자동으로 해당 키를 삭제한다.

TTL을 설정할 때는 데이터의 특성을 고려해야 한다. 자주 바뀌는 데이터(재고, 가격)는 TTL을 짧게, 잘 안 바뀌는 데이터(상품 카테고리, 공지사항)는 TTL을 길게 설정한다. TTL 없이 저장하면 메모리가 계속 쌓이다가 장애로 이어질 수 있다.

##### 캐시 교체 정책
메모리가 꽉 찼을 때 어떤 데이터를 삭제할지 결정하는 정책이다. Redis의 `maxmemory-policy` 설정으로 지정한다.

**LRU(Least Recently Used)** 는 가장 오랫동안 사용되지 않은 데이터를 삭제한다. 일반적인 캐시 용도에서 가장 많이 사용한다.

**LFU(Least Frequently Used)** 는 사용 빈도가 가장 낮은 데이터를 삭제한다. 자주 쓰이는 데이터를 더 오래 보존하고 싶을 때 유리하다.

**noeviction**은 메모리가 꽉 차도 삭제하지 않고 쓰기 요청에 에러를 반환한다. 세션 스토어처럼 데이터가 절대 유실되면 안 되는 경우에 사용한다.

#### 캐시 스탬피드 (Cache Stampede)

TTL이 만료된 순간 수많은 요청이 동시에 Cache Miss를 경험하고, 모두 DB로 몰려가는 현상이다. 트래픽이 많은 서비스에서 캐시가 만료되는 순간 DB가 폭발적인 부하를 받아 장애로 이어질 수 있다.

해결 방법은 크게 세 가지다. 첫 번째는 **Mutex Lock**으로, 첫 번째 요청만 DB를 조회하고 나머지는 대기하게 한다. 두 번째는 **PER(Probabilistic Early Recomputation)** 으로, TTL 만료 전에 확률적으로 미리 갱신하는 방식이다. 세 번째는 **TTL에 랜덤값을 추가**해 동일한 시점에 여러 키가 한꺼번에 만료되는 걸 방지하는 방식이다.


### 세션 스토어

#### 왜 Redis를 세션 저장소로 쓰는가

로그인 세션을 서버 메모리에 저장하면 서버가 한 대일 때는 문제가 없다. 하지만 서버가 여러 대로 늘어나면 문제가 생긴다. A 서버에서 로그인한 사용자가 다음 요청을 B 서버로 보내면, B 서버 메모리에는 세션 정보가 없어서 로그인이 풀려버린다.

이 문제를 해결하는 방법은 두 가지다. 하나는 Sticky Session으로, 같은 사용자의 요청을 항상 같은 서버로 보내는 방식이다. 하지만 특정 서버에 부하가 집중되고, 해당 서버가 죽으면 세션도 함께 사라진다. 다른 하나가 Redis 같은 외부 저장소에 세션을 저장하는 방식이다. 어떤 서버로 요청이 가든 Redis에서 세션을 꺼내면 되므로 서버를 자유롭게 늘리고 줄일 수 있다.

#### 분산 환경에서의 세션 공유 구조

```
[사용자 요청]
      ↓
[로드 밸런서]
   ↙       ↘
[서버 A]  [서버 B]
      ↘  ↙
    [Redis]
   (세션 저장소)
```

세션 데이터는 보통 Hash 자료구조로 저장하고, TTL을 설정해 일정 시간 이후 자동 만료되도록 한다. 사용자가 활동할 때마다 TTL을 갱신하면 자연스럽게 세션 유지 기능이 구현된다.


### 분산 환경 이슈

#### 분산 락 (Distributed Lock)
여러 서버가 동시에 같은 자원에 접근할 때 충돌을 막기 위해 사용한다. 예를 들어 재고가 1개 남은 상품에 동시에 두 명이 주문을 넣는 상황을 생각해보자. 각 서버가 독립적으로 재고를 확인하고 차감하면 재고가 -1이 되는 문제가 발생한다.

Redis의 SETNX(SET if Not eXists) 명령을 활용해 분산 락을 구현할 수 있다.

```
# 락 획득 시도 (10초 TTL)
SET lock:order:item:100 "server-A" NX EX 10

# 반환값이 OK면 락 획득 성공, nil이면 다른 서버가 락을 보유 중
```

NX 옵션은 키가 없을 때만 저장하기 때문에, 한 서버만 락을 획득할 수 있다. EX로 TTL을 설정하는 이유는 락을 획득한 서버가 죽어도 일정 시간 후 자동으로 락이 해제되도록 하기 위해서다.

실무에서는 이 로직을 직접 구현하기보다 Redisson(Java), redis-py-lock(Python) 같은 라이브러리를 사용하는 경우가 많다. 락 획득 실패 시 재시도 로직, 락 연장 등 세부적인 처리가 복잡하기 때문이다.

#### 동시성 문제 처리
Redis는 단일 스레드로 명령을 처리하기 때문에 개별 명령은 원자적으로 실행된다. INCR 명령이 안전하게 카운팅되는 것도 이 때문이다. 하지만 여러 명령을 묶어서 실행할 때는 그 사이에 다른 명령이 끼어들 수 있다.

이때 사용하는 게 **트랜잭션(MULTI/EXEC)** 이다.

```
MULTI           # 트랜잭션 시작
DECR stock:100  # 재고 차감
INCR order:100  # 주문 카운트 증가
EXEC            # 한 번에 실행
```

MULTI와 EXEC 사이의 명령들은 큐에 쌓였다가 EXEC 시점에 한꺼번에 실행된다. 더 복잡한 로직이 필요하다면 Lua 스크립트를 사용해 여러 명령을 원자적으로 처리할 수 있다.


### 메시지 브로커로서의 Redis

#### Pub/Sub
발행자(Publisher)가 채널에 메시지를 보내면, 해당 채널을 구독한 모든 구독자(Subscriber)가 메시지를 받는 방식이다.

```
# 구독자
SUBSCRIBE channel:notification

# 발행자
PUBLISH channel:notification "새로운 알림이 있습니다"
```

실시간 알림, 채팅, 이벤트 브로드캐스트에 사용된다. 다만 Pub/Sub는 메시지를 저장하지 않기 때문에, 구독자가 오프라인이었다면 그 사이의 메시지는 유실된다.

#### Stream
Redis 5.0부터 추가된 자료구조로, 메시지를 디스크에 저장하고 Consumer Group 개념을 지원한다. Kafka와 유사하지만 더 가볍게 사용할 수 있다.

Pub/Sub와의 차이점은 메시지가 저장된다는 것이다. 구독자가 오프라인이었다가 다시 연결되면 밀린 메시지를 처리할 수 있다. 또한 Consumer Group을 사용해 여러 소비자가 메시지를 분산 처리할 수 있다.

Kafka와의 차이점은 규모와 내구성이다. Kafka는 수백만 TPS를 처리하고 디스크 기반으로 장기간 메시지를 보관할 수 있는 반면, Redis Stream은 메모리 기반이라 용량 제한이 있고 대규모 메시지 처리에는 적합하지 않다. 간단한 이벤트 처리나 소규모 메시지 큐에는 Redis Stream이, 대규모 데이터 파이프라인에는 Kafka가 적합하다.


### 운영/장애 대응

#### 메모리 모니터링과 maxmemory 정책
Redis는 메모리 기반이기 때문에 메모리 관리가 가장 중요하다. `INFO memory` 명령으로 현재 메모리 사용량을 확인할 수 있다.

`maxmemory` 설정으로 Redis가 사용할 수 있는 최대 메모리를 제한한다. 이 한도를 넘었을 때의 동작은 앞서 설명한 `maxmemory-policy`로 제어한다. 실무에서는 서버 전체 메모리의 60~70% 수준으로 설정해, 메모리 부족으로 인한 OS 스왑이 발생하지 않도록 여유를 두는 것이 중요하다.

#### 핫키 (Hot Key) 문제
특정 키에 요청이 집중되는 현상이다. 예를 들어 인기 상품의 상세 정보 키에 초당 수만 건의 요청이 몰리면, Redis 단일 스레드 특성상 해당 요청 처리에 병목이 생긴다.

해결 방법으로는 로컬 캐시 계층을 추가하는 것이 있다. 각 애플리케이션 서버의 메모리에도 작은 캐시를 두어 Redis 요청 자체를 줄이는 방식이다. 또는 키를 여러 개로 샤딩해(예: `hot:item:100:1`, `hot:item:100:2`) 요청을 분산시키기도 한다.

#### Redis Cluster vs Sentinel
**Sentinel**은 마스터-슬레이브 구조에서 마스터가 죽었을 때 자동으로 슬레이브를 마스터로 승격시켜주는 고가용성 솔루션이다. 데이터 복제와 자동 장애 복구가 목적이다.

**Cluster**는 데이터를 여러 노드에 분산 저장하는 방식이다. 16384개의 슬롯을 나눠 각 노드가 담당하기 때문에 수평적으로 확장이 가능하다. 대규모 서비스에서 단일 Redis 인스턴스의 메모리 한계를 넘어야 할 때 사용한다.

정리하면 Sentinel은 가용성을 위한 것이고, Cluster는 확장성을 위한 것이다. 두 가지를 함께 구성할 수도 있다.

#### 캐시 히트율 측정
캐시 히트율(Cache Hit Rate)은 전체 요청 중 캐시에서 응답한 비율이다. 히트율이 낮으면 캐시가 제대로 동작하지 않는 것이므로 TTL 설정이나 캐시 대상 선정을 재검토해야 한다.

```
INFO stats 명령으로 확인
keyspace_hits: 캐시 히트 수
keyspace_misses: 캐시 미스 수

히트율 = hits / (hits + misses) * 100
```

일반적으로 80% 이상이면 양호한 수준으로 본다. 히트율이 지속적으로 낮다면 자주 조회되는 데이터가 TTL 만료 전에 eviction되고 있는 건 아닌지, 캐시 키 설계가 올바른지 점검해야 한다.
